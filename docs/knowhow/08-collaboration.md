# 08 共同作業の仕組み

## 考え方

- 協力者は自分の Claude に「`VERIFY.md`（または `COLLAB.md`）に従って、未着手の作業を1件やって」と頼むだけ。手順は手順書に、決まりは CLAUDE.md に、状態は Issue に置く。
- 協力者にリポジトリの書き込み権限は渡さない。**Issue のコメントのコマンド**だけで担当・進み具合・提出を記録し、ボット（`.github/workflows/task-bot.yml`）がラベルと本文を書き換える。
- 共同編集者（管理者の別アカウントや信頼できる人）は main に直接 push してよい。

## コマンド（コメントの行頭に書く）

| コマンド | 意味 |
|---|---|
| `/claim` | 担当する（未着手 → 担当中）。先に誰かが担当していればボットが知らせる |
| `/check 番号 ok\|ng\|hold` | 確認項目に ✅ ❌ ⚠️ を付ける（hold＝人の目で確認が必要） |
| `/submit URL ひとこと` | 成果物を提出（自分のフォークの枝・コミット）→ 確認待ち |
| `/done ひとこと` | 終わり。検証は全部 ok なら完了、そうでなければ要人間確認。検証以外は確認待ち |
| `/human 理由` / `/release` | 人の判断が必要 ／ 担当をやめる（3日報告が無いと自動で戻る） |
| `/items`・`/type`・`/accept`・`/reject` | 管理者のみ：確認項目の追加・種類の変更・取り込み・差し戻し |

- 作業の種類（ラベル）: 検証・調査・実装・素材・資料。状態: 未着手 → 担当中 → 確認待ち → 完了（要人間確認）。
- 担当者・時刻・提出物・履歴は Issue 本文の末尾の見えないメモ（`<!-- task-state … -->`）に入る。まとめページはそれを読む。

## まとめページ（docs/status.html）

- タブ: 全体（種類×状態の表・最近の動き）／要望／種類別／協力者（Issue での活動とフォークから自動で一覧。紹介は docs/collaborators.json）／始め方（役割ごとに添付するものと送る一文）。
- 開くたびに GitHub の API から読む（ログイン不要、1時間60回まで）。

## 要望（改善したいこと）

- まとめページの「要望」タブから、協力者の声や人から聞いた話を貼り付けて送る → Issue（ラベル「要望」）になり、ボットが自動で検証タスク（基本の確認項目3つ）にする。ファイルは GitHub の画面で添付。

## データの受け渡し

- 公開してよいもの（ソース・解析メモ・自作の素材・翻訳）: 協力者のフォークの枝 `task-<Issue番号>` に置いて `/submit`。管理者側の Claude が取り寄せて確かめ、取り込む。
- ROM 由来のもの: 置かない。作り方（スクリプトと入力列）を共有する（06）。どうしても必要なら、非公開のリポジトリに管理者を招待して受け渡す。

## 提出の形（調査・実装）

- 「何を知りたいか／どう測ったか／対照／結果」の4点を必ず書き、**単体で動く再現スクリプト**を付ける。ROM の中身を渡さずに、相手が自分の純正ROMで同じ数字を出せる。確かめる側が再実行しなくても判断しやすい。
- 協力者が作業するのは管理者の夜中かもしれない。手順書（VERIFY.md・COLLAB.md）とボットだけで、管理者を起こさずに最後まで進められる形にしておく。

## Windows の協力者

- Git Bash（MSYS）から `gh` でコメントすると、行頭の `/claim` が `C:/Program Files/Git/claim` に化ける（パス変換）。ボットからは「担当者だけが使えます」と返り、権限の問題に見えて分かりにくい。ボットで化けた形を受け付け、手順書に「PowerShell から送るか `MSYS_NO_PATHCONV=1`」と書いておく。
