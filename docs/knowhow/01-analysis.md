# 01 解析の進め方

## ROM を1本にする（68000 の例。ほかの CPU は 09-cpus.md）

- 68000 基板のプログラム ROM は、16bit を **偶数バイトの ROM と奇数バイトの ROM** に分けて載せていることが多い。交互に並べて1本にしてから読む（`tools/romkit.py` の `il()`）。改造後は `split()` で分け直す。
- どちらが偶数かは MAME のドライバの `ROM_LOAD16_BYTE` の並び（先に書かれ、オフセットが偶数の方）で分かる。
- サブ CPU・サウンド CPU（Z80 など）がある基板は、それぞれ別の ROM。改造に関係するものだけ扱う。

## まず見るところ

1. **ベクタ**: 先頭の long が SSP、次が PC（リセット後の開始番地）。レベル N の割り込みベクタも見る。ほぼ全部が同じ無限ループなら、使っていない割り込み。
2. **全域の逆アセンブル**（`tools/d68.py`）を出して、grep できるようにしておく。RAM 番地の参照、`cmpi` の定数、テーブルを指す `lea` を探す。
3. **メインの状態機械**: VBL などの割り込みの中で「モード変数 → 4バイトのテーブル → `jsr (a6)`」の形が定番。モード／状態／サブ状態の3段になっていることが多い。テーブルは long の並びで、逆アセンブルすると `ori` などに化けるので16進で読む。

## RAM の意味を特定する（実測が基本）

- 条件を変えて（面・装備・残機・ボム…）RAM を比べる。MAME を画面なしで回し、決まったフレームでメモリを保存して差分を取る（`lua/run.lua` の `DUMPAT`/`DUMP`、`WATCH`）。
- **誰が書いたか**を知るのが一番大事。書き込みを見張って、書いた命令の PC を記録する（MAME の Lua の write tap、または自作エミュレータの書き込みフック）。
- 自分の変数の置き場所は「長時間回しても一度も書かれない RAM」から選ぶ。**ゲーム開始時・死亡時・面の開始時にクリアされる範囲は避ける**（gradius3 では、死亡・再開時に使われる場所に置いたら、面が3面に飛ぶバグになった）。死亡をまたいで残るか必ず確かめる。

## ゲームにもともとある仕組みを使う（最重要）

- 面の持ち越し装備の復元、死亡時の復活地点テーブルと再開ルーチンなど、**ゲーム自身の処理をフラグを立てて呼ばせれば**、装備の注入や面の途中からの開始が少ない改造で安全にできる。
- 注入するタイミングは「ゲーム開始時の初期化（クリア）の後」。
- 停止区間（ボス前などでスクロールが止まる所）の進み方が時間で決まっている場合、開始位置をずらしても飛ばせない（gradius3 の 3面）。時間のカウンタも一緒に進めるか、別の方法が要る。

## 強制して確かめる

- 状態変数を直接書いて（例: ゲームオーバー状態）遷移が最後まで流れ、デモ画面に戻るかを実測する。
- 判定の処理は「入力・状態を強制してフックの分岐を観測する」（例: 残り弾数を0に書き換えて、発射できるかを見る）。

## 画面の中身を文字で見る

- タイルマップ RAM のバイト対（属性・コード）を文字に戻して画面をダンプすれば、レイアウトの確認に画像は要らない。
- 画像が要るときは MAME のスナップショットを使う（`lua/run.lua` の `SNAP`）。自前でタイル ROM をデコードして描く場合は、回転・パレットの基準に注意（あくまで近似）。

## 隠しパラメータ（ランクなど）

- 複数のテーブルを足してクランプしてシフトするような「集計して1か所に入れる」ルーチンを探し、条件を変えて格納先を実測する。
